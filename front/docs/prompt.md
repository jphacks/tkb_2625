# 依頼
あなたはUI/UXデザインとReact実装に詳しいフロントエンドエンジニアです。
以下の要件に沿って、ロゲイニング大会の参加者がスマートフォンで使うWebアプリを実装してください。
参加者がチェックポイントを探し、写真を提出し、審査状況と獲得ポイントを確認できることを目的とします。
デザイン案だけでなく、実行可能なコードを作成してください。

# 実装方針と技術スタック
- React、JavaScript、React Router、Tailwind CSSを使用する。HTMLはJSXで記述し、必要に応じてCSSを補う。
- 既存プロジェクトがある場合は、その構成・依存関係・実装方針を確認して活用する。新規作成の場合はViteを使用する。
- モバイルファーストで設計し、タブレット・PCでも利用できるレスポンシブ構成にする。
- バックエンドやAPIの指定がないため、まずはモックデータで主要操作が動くプロトタイプを作る。
- APIへの置き換えが容易になるよう、データ取得・更新処理をUIから分離する。認証や複数端末間の同期は今回の必須範囲に含めない。
- 要件にない大きな機能は追加せず、不明点は合理的な仮定を置いて進め、採用した仮定を最後に明記する。

# 画面構成と共通表示
- 最上部に、チーム名・大会の残り時間・現在の獲得ポイントを表示する。
- 残り時間は大会終了日時から計算して更新し、終了後は0で止めて写真の提出を無効にする。
- 共通表示の下に「カード」「チーム」「マップ」の切り替えタブを置く。
- React Routerで各タブにURLを割り当て、直接アクセスやブラウザの戻る・進むに対応する。
- タブの定義を配列などで管理し、後から画面を追加しやすくする。

## カード画面
- チェックポイントを画像付きカードで一覧表示する。
- 幅375px程度のスマートフォンでは原則3列とし、狭い画面では読みやすさを優先して列数を減らす。横スクロールは発生させない。
- カードには、チェックポイント名・配点・目標画像・提出ステータスを表示する。
- タップまたはクリックで詳細モーダルを開く。ホバーだけに依存せず、キーボードでも操作できるようにする。
- 詳細では、目標画像と提出画像を比較できるようにする。スマートフォンでは上下、十分な幅がある場合は左右に並べる。
- カメラ撮影または画像ファイルの選択、提出前のプレビュー、画像の差し替え、提出操作に対応する。
- 対応する画像形式と容量上限を明示し、不正なファイルや画像未選択時には分かりやすいエラーを表示する。
- 提出ステータスは以下の4種類とし、色に加えてラベルやアイコンでも識別できるようにする。
  - 未提出：まだ写真を提出していない。
  - 審査中：写真を提出済みで、結果を待っている。
  - 不可：提出が不承認。理由を表示し、写真を再提出できる。
  - 可：提出が承認され、配点が獲得ポイントに加算されている。
- 「未提出 → 審査中 → 可／不可」「不可 → 再提出 → 審査中」の状態遷移を扱う。審査中・承認済みの重複提出は防止する。
- ステータスによる絞り込みと、配点・名前・ステータスによる並び替えを用意する。並び順をUI上に明示する。
- 該当カードがない場合や提出画像がない場合にも、適切な案内を表示する。

## チーム画面
- チーム名、獲得ポイント、メンバー一覧、写真の提出履歴を表示する。
- 履歴にはチェックポイント名・提出日時・審査状況・獲得ポイントを表示し、新しい順に並べる。
- 再提出は過去の履歴を残す。ポイントはチェックポイントごとに一度だけ加算し、ヘッダー・カード・チーム画面で同じ状態を参照する。

## マップ画面
- 既存の地図ライブラリや地図サービスを利用し、現在位置、チェックポイントの位置、GPSで記録した移動経路を表示する。
- 利用するライブラリ・サービスと、APIキーの要否・地図の出典表記を明記する。秘密情報をコードに埋め込まない。
- 位置情報の取得はユーザーの「記録開始」操作で開始し、「記録停止」操作と画面の離脱時に監視を解除する。
- 現在位置へ戻る操作と、方位を確認できるコンパス表示を用意する。地図の北方向と端末の向きを区別する。
- 位置情報や方位センサーが未対応・許可されていない場合は、その状態と代替表示を案内する。取得できない値を実測値として表示しない。
- 実際の位置情報を取得できない環境でも確認できるよう、実データと明確に区別したデモ表示を用意する。
- HTTPSや端末側の許可など、動作に必要な条件をREADMEに記載する。バックグラウンドでの継続記録は保証範囲に含めない。

## 管理者画面（追加要件）
- 必須の参加者向け機能が完成した後、可能であれば `/admin` に管理者画面を実装する。
- 提出画像の確認、承認・不承認、不承認理由の入力、チームのポイント確認ができるようにする。
- 審査結果を参加者画面に反映し、同じ提出を繰り返し承認してもポイントが重複加算されないようにする。
- モック実装ではデモ用管理画面であることを明示する。本番での管理者認証・権限制御は別途必要であり、URLを分けるだけで保護できるとは扱わない。
- 管理者画面を実装しない場合も、デモ操作で各審査状態を確認できる手段を用意する。

# デザインと操作性
- 角丸を使わず、直線的でフラットなデザインにする。
- 落ち着いた配色とし、基本色は相性のよい3色程度に絞る。ステータスやエラーの色は別途使用してよい。
- 強すぎる色の対比は避けつつ、文字と背景には十分なコントラストを確保する。
- 文字の可読性とタップしやすさを優先する。主要な操作領域は原則44px以上を確保する。
- ボタンや入力欄に適切なラベルとフォーカス表示を設け、モーダルは閉じる操作・フォーカス管理・Escapeキーに対応する。
- 処理中・空の状態・エラー・権限拒否の状態を用意し、次にできる操作を伝える。

# データと検証
- チーム、大会終了日時、メンバー、チェックポイント、提出履歴を構造化し、チェックポイントはID・名前・配点・座標・目標画像・提出状況を持たせる。
- 4種類のステータスと再提出履歴を確認できるサンプルデータを用意する。
- 再読み込み時に何が保持されるかを明示する。モックデータの保存方法は簡潔にし、画像を含む永続化は必要に応じて判断する。
- 少なくとも以下を確認し、実行した確認と未確認の項目を報告する。
  - スマートフォン幅で表示が崩れず、タブと詳細モーダルを操作できる。
  - 画像の選択・提出・不承認後の再提出ができる。
  - 審査結果と獲得ポイントが各画面で一致し、重複加算されない。
  - 絞り込み・並び替え・大会終了時の提出制限が動作する。
  - 位置情報が許可されない場合も、アプリを操作できる。
  - ビルドが成功する。
